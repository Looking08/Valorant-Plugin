逆向与实现报告

掌瓦（掌上无畏契约）扫码登录完整方案

项目 Valorant-Plugin（TRSS-Yunzai / Yunzai V3）
逆向目标 掌上无畏契约 2.9.0 · com.tencent.apps.valorant
验证状态 微信 / QQ 两条链路均已真机扫码并取到战绩数据

0. 一句话结论

扫码登录能做，而且两条路都能做：微信零配置、纯 HTTP；QQ 需要一台浏览器。 拿到的凭证与抓包导入完全等价（cookie + scene），可以直接查战绩。

本文记录的是完整的推导过程、接口契约、踩过的坑和验证数据，不是"据说可以"。

2. 逆向对象与方法

项 值
文件 掌上无畏契约_2.9.0.APK（111 MB）
包名 com.tencent.apps.valorant
架构 原生 Kotlin + React Native（libhermes / libfabricjni）+ 腾讯 QTL（掌盟）框架
DEX 17 个，约 5.75 万个类 / 37 万个方法
工具 jadx 1.5.6（单类反编译）+ 自写 DEX 解析器（reapk/dexscan.py，做字符串与交叉引用定向提取）

方法上的两个关键点：

  1. 不要全量反编译。5.75 万个类跑 jadx 要半小时以上，且大部分是广告/容器代码。 正确做法是先扫字符串池定位特征串，再用 DEX 交叉引用找到引用它的类，最后只反编译那几个类。
  2. Gson 默认用字段名当 JSON key。所以只要从 DEX 里读到 LoginByWXProtocol$Params 的字段声明，就等于拿到了服务端的完整请求契约，不需要抓包也能写对请求体。

整件事能成立的前提，也是最容易看漏的一点：

login_by_qq / login_by_wechat 的请求体里没有 secret。 code→openid 的交换是掌瓦服务端用它自己的 AppSecret 做的。 所以我们不需要腾讯的密钥，只需要「一张票」——这正是扫码能替代抓包的原因。

4. 微信扫码：走的是「扫码 SDK」，不是「网站应用」

4.1 两套微信扫码，别搞混

这是本方案最早踩的坑，也是我一度错误判断"微信做不到"的原因：

网站应用 connect/qrconnect 扫码 SDK connect/sdk/qrconnect
redirect_uri 必须有，且要在开放平台备案 没有这个概念
门槛 appid 归属 + 域名备案 一串 sdk_ticket + sha1 签名
code 从哪来 回调到你的服务器 长轮询接口直接吐给你
掌瓦能用吗 ❌ 回调域是腾讯的 ✅

手机 App 里那个「用微信扫一扫登录」用的就是后者。掌瓦复用它，我们原样复用掌瓦。

4.2 逆向来源

classes8.dex → com.tencent.wglogin.authsuite.c，方法 a(Activity, a)（内部叫 loginWXByQRCode）：

new GetWXServerTicketProtocol().post(activity, … {
    public void onSuccess(GetWXServerTicketResult r, boolean z) {
        String appid     = com.tencent.wglogin.authsuite.util.a.b;  // 运行时注入
        String noncestr  = e.a(6);
        String timestamp = (System.currentTimeMillis() / 1000) + "";
        String origin = "appid=" + appid + "&noncestr=" + noncestr
                      + "&sdk_ticket=" + r.ticket + "&timestamp=" + timestamp;
        String sign = f.a(origin);                                  // sha1 hex
        DiffDevOAuthFactory.getDiffDevOAuth()
            .auth(appid, "snsapi_userinfo", noncestr, timestamp, sign, listener);
    }
});

DiffDevOAuth 是微信官方 libammsdk 里的类，它内部做的事正好对应 DEX 里那两条 URL：

https://open.weixin.qq.com/connect/sdk/qrconnect?appid=%s&noncestr=%s&timestamp=%s&scope=%s&signature=%s
https://long.open.weixin.qq.com/connect/l/qrconnect?f=json&uuid=%s

4.3 取票（这一步是整个方案的关键）

POST https://app.mval.qq.com/go/auth/get_sdk_ticket?source_game_zone=agame&game_zone=agame
Content-Type: application/json
Cookie: clientType=9; openid=null; access_token=null

{"clienttype":9,"config_params":{"client_dev_name":"23117RK66C","lang_type":0}}

免鉴权，直接返回：

{"data":{"ticket":"qeuRRdzufZaOpdhfU2Q4gGbgoxq-NLbBLoPmh9nUqycSJTMoFHaQ4dN1XcR9TaOt…"},"result":0}

注意：必须是 POST + JSON body，GET 会返回 404 page not found。

4.4 签名

signature = sha1("appid={appid}&noncestr={noncestr}&sdk_ticket={ticket}&timestamp={timestamp}")

参数顺序不能变，这是微信的规则。noncestr 是随机串（App 里是 6 位，我们用 16 位 hex 也可以）。

4.5 出码

GET https://open.weixin.qq.com/connect/sdk/qrconnect
    ?appid=wxcbb49f1f39656c2a
    &noncestr={noncestr}
    &timestamp={timestamp}
    &scope=snsapi_userinfo
    &signature={signature}

成功返回（实测 68 700 字节）：

{
  "errcode": 0,
  "uuid": "061lJR7z2qTgnl2d",
  "appname": "掌上无畏契约",
  "qrcode": { "qrcodebase64": "/9j/4AAQSkZJRgABAQ…" }
}

appname 回显「掌上无畏契约」——这是服务端替我们确认了 appid 归属正确，比任何静态分析都硬。 图片是 JPEG（/9j/ 开头，472×472），不是 PNG。

失败时 errcode=40001 表示签名不对或 ticket 过期。

4.6 轮询状态

GET https://long.open.weixin.qq.com/connect/l/qrconnect?f=json&uuid={uuid}
wx_errcode 含义 处理
408 未扫码 继续等
404 已扫，等待手机确认 提示用户点确认
405 已确认，带 wx_code 拿 code 去换票
402 二维码过期 重新出码
403 用户取消 结束

⚠️ 只有 405 才带 code。404 只是"扫了但没点确认"，此时去换票必然失败。

4.7 换掌瓦凭证

POST https://app.mval.qq.com/go/auth/login_by_wechat?source_game_zone=agame&game_zone=agame
Cookie: clientType=9; openid=null; access_token=null

{
  "clienttype": 9,

5. QQ 扫码：页面式授权，绕开被黑洞的那一跳

5.1 我最初错在哪

第一版是纯 HTTP 手工追 ptqrlogin → check_sig → auth://，卡在 check_sig 上。 那台机器的 DNS 确实被指到 0.0.0.1，四个公共 DNS 结果一致：

$ dig +short ptlogin4.openmobile.qq.com @223.5.5.5    → 0.0.0.1
$ dig +short ptlogin4.graph.qq.com      @119.29.29.29 → 0.0.0.1
$ dig +short ptlogin4.web.qq.com        @1.1.1.1      → 0.0.0.1
$ curl https://ptlogin4.openmobile.qq.com/            → 000（连不上）

我据此得出「换票前置机已下线，扫码做不到」——错在把这条路当成了唯一的路。

5.2 真正的落地页是 m_authlist

m_authorize 返回的不是二维码，而是一个跳转页，里面带着服务端下发的 h5sig：

var src = "https://xui.ptlogin2.qq.com/cgi-bin/xlogin?appid=716027609
          &pt_3rd_aid=102061775&daid=381&…&h5sig=MfBler9YgYCaIkB91wdEHEiRvJzgTqz6JTw7_14YvYM&loginty=7";
location.replace(src);

loginty=7 + h5sig 走的是 openapi 版授权。扫码确认后，页面去的是：

GET https://openmobile.qq.com/oauth2.0/m_authlist?…&loginty=7
→ HTTP 200，4246 字节
→ <p id="auth_tips">掌上无畏契约将获得以下权限:</p>

这台是活的。 授权在 openmobile.qq.com 域内完成， check_sig 是旧流程（loginty=6）的落点。走错了分支，才会撞上那三台死机器。

5.3 方案：让浏览器跑，我们只听

1  GET  openmobile.qq.com/oauth2.0/m_authorize?client_id=102061775
        &scope=all&redirect_uri=auth://tauth.qq.com/&response_type=token&style=qr
2  页面 JS 自动跳转 → xui.ptlogin2.qq.com 渲染二维码
3  用户扫码 + 手机确认
4  页面内完成授权 → 跳 auth://tauth.qq.com/#access_token=…&pay_token=…
5  拦截这个回调，取 access_token
6  GET  graph.qq.com/oauth2.0/me?access_token=…&fmt=json  → openid
7  POST login_by_qq → 掌瓦凭证

三处信号同时监听（哪个先响算哪个，缺一不可）：

信号 命中场景
page.on('request') auth:// 协议导航
page.on('framenavigated') 导航不一定产生 request 事件
轮询 location.href 兜底，防上面两个都没触发

保险丝：一旦发现浏览器要去访问那三台黑洞主机，就地 abort， 把同一个 path/query 改投到活着的 ptlogin4.qq.com 集群 （实测：无效 sigx 会 302 到 www.qq.com，说明它认这套参数）。

5.4 出码细节（踩过的坑）

页面上的真码是：

<img id="qrimg" src="https://xui.ptlogin2.qq.com/ssl/ptqrshow?s=8&e=0&appid=716027609&…">

但页面上还有一个空的 <img id="imgVerify">。 第一版按 img 标签取第一张，抓到了那个空元素，截出一张 549 字节的空白图。

正确做法：选择器写 #qrimg，并且回源取原图—— 拿页面当前 cookie 去请求那个 ptqrshow 地址，得到 264×264 原始 PNG， 比截屏清晰、也不受页面缩放影响（同一个 qrsig 反复请求是幂等的，拿到的是同一张码）。

5.5 回调里没有 openid

response_type=token 的回调只有 access_token / pay_token，没有 openid。 要另外用标准接口换：

GET https://graph.qq.com/oauth2.0/me?access_token=…&fmt=json
→ {"openid":"…","client_id":"…"}

老版本会返回 JSONP callback( {"openid":"…"} );，需要兼容。

7. 工程实现

7.1 模块结构

bridge/login/
├── index.js      适配器注册表（qq / wx，可选 wxweb / mock）
├── session.js    会话状态机 + 资源释放（release）
├── qq.js         QQ 适配器：浏览器优先，纯 HTTP 兜底
├── qqpage.js     └─ 页面式授权（真浏览器跑 m_authorize）
├── browser.js    └─ 浏览器获取（puppeteer-core / puppeteer / 云崽宿主）
├── wechat.js     微信适配器：扫码 SDK，纯 HTTP
├── wxqr.js       └─ sdk_ticket → 签名 → 出码 → 轮询
├── exchange.js   code / token → 掌瓦凭证（login_by_qq / login_by_wechat）
└── mock.js       假登录（仅 LOGIN_MOCK=1）

分层约定：插件只管交互（出图、轮询、提示），网关持有会话， provider 负责 saveLogin()。加一个新平台 = 加一个 adap ter + 注册一行，插件不用改。

7.2 状态机

waiting ──扫码──> scanned ──确认──> confirmed ──commit──> 落库
   │                  │
   ├──超时──────────> expired
   ├──上游不认参数──> blocked
   └──用户取消──────> cancelled

blocked 是刻意设计的状态，不是异常补丁：上游不认这套请求时， 让用户干等到超时是最差的选择，连续 5 次空响应就承认失败并给出下一步建议。

7.3 凭证落库与多人隔离

bridge/mate.json              基础配置（接口路径、武器表）—— 部署者一份
bridge/accounts/<user>.json   每个人的 cookie + scene —— 一人一份

saveCredential() 会先落盘再验证：立刻拿这份 cookie 打一次真实请求， 认出角色名与 role_id；验证失败则删掉刚写的文件，不留半份坏凭证。

这条"绝不偷偷用 base 凭证"的规则很重要——否则每个群友都会看到机器人主人的战绩。

9. 失效点与维护手册

按"多久会坏"排序：

项 风险 坏了怎么办
jsver 腾讯每几周换一次 QQ 纯 HTTP 版从 xlogin 页面现抓；浏览器版不需要
mcode / device 随客户端版本变 重新从 APK 提，或抓包看 UA
signature / h5sig 一次性签名 浏览器版由页面自己生成；微信版每次现算
sdk_ticket 有有效期（分钟级） 每次出码都重新取一次，不要缓存
scene 会话级 blob，与"哪一页"绑定 列表/概览用一个（175 字符），单局详情用另一个（91 字符）
凭证 硬 3 天过期 重扫一次（微信 30 秒），或重新抓包

排障入口：

node tools/test-login.mjs wx                 # 微信：出码 + 状态机
node tools/test-login.mjs wx --save --query  # 微信：落库 + 查最近 3 场
