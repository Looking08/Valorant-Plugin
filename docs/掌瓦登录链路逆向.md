# 掌上无畏契约 2.9.0 登录链路逆向

> 目标：搞清楚「掌瓦」到底怎么登录，然后判断 `Valorant-Plugin` 能不能把微信/QQ 扫码做成服务端可用的路。
> 结论在第一节，证据在后面。**所有结论都标了是「静态分析」还是「运行时实测」。**

---

## 一、结论先行

> **⚠️ 本节在第二轮逆向后被更正过。** 第一版结论是「QQ 和微信扫码都做不了」，
> 那是因为当时只找到了一条路就下了判断。第二轮补上了两条关键发现：
>
> 1. **QQ**：带 `loginty=7` + `h5sig` 的新流程**不走** `check_sig`，走 `m_authlist`（活主机）；
> 2. **微信**：除了要白名单的 `qrconnect`，还有**不需要白名单**的 `sdk/qrconnect`（扫码 SDK），
>    而它的 `sdk_ticket` 掌瓦自己开了个免鉴权的取票接口。
>
> 所以现在两条扫码链路都实现了，而且都不用你提供 secret。

| 路线 | 能不能做成服务端扫码 | 关键点 | 证据 |
|---|---|---|---|
| **QQ 扫码** | ✅ 能（要浏览器） | 用真浏览器跑 `m_authorize`，页面自己完成授权并吐 `auth://`；监听回调拿 token | 实测出码 264×264 |
| **微信扫码** | ✅ 能（纯 HTTP，零配置） | `get_sdk_ticket` → `sdk/qrconnect` 出码 → 轮询拿 code | 实测出码 62KB JPEG，appname 回显「掌上无畏契约」 |
| **抓包导入**（现有功能） | ✅ 可用 | 无（手工成本高，票据硬 3 天） | 项目已有 |
| **手动喂 token/code** | ✅ 可用 | 需要你从别处拿一份合法 token | `tools/mval-login.mjs` |
| **设备侧提取登录态** | ⚠️ 可行但要 root | 掌瓦把凭证存在 MMKV 的 `wg_license_cache` 里 | 静态分析 |

**为什么会误判（留作教训）**：

- QQ 那条，我停在 `ptqrlogin` 返回的 `check_sig` 上，而那台主机确实被 DNS 黑洞
  （四个公共 DNS 一致返回 `0.0.0.1`，直连失败）。但 `check_sig` 只是**旧流程**的落点；
  带 `h5sig` 的新流程落到 `openmobile.qq.com/oauth2.0/m_authlist`，那台是活的。
- 微信那条，我看到 `login_info` 里没有 secret，就认定「code 必须由掌瓦 appid 签发，
  而那个 appid 的回调域在腾讯手里」。前半句对，后半句错 —— 扫码 SDK 压根没有回调域这个概念。

一句话：**结论不是「腾讯把门关了」，是「我找错了门」。**

## 五、运行时实测（这是最关键的一节）

### 5.1 出码是好的

```
xlogin  → HTTP 200，下发 pt_login_sig / pt_user_id / ptui_identifier
ptqrshow → HTTP 200，387 字节 PNG，**264×264**（够扫）
jsver   → 3ea7b82c   ← 注意：项目里硬编码的 28d22679 已经过期了
```

### 5.2 换票接口是好的，字段全对

拿假 token 打 `login_by_qq`，服务端把**我们发的完整请求体原样回显**了：

```
{"errMsg":"login by qq fail ret=10104, params:{
  "clienttype":9,"clientip":0,"mappid":10200,
  "login_info":{"uin":0,"openid":"PROBE_INVALID_OPENID","appid":102061775,
                "sig":"PROBE_INVALID_TOKEN","qq_info_type":5,"is_new":0},
  "mcode":"132f0a77...","config_params":{"lang_type":0,
                "client_dev_name":"23117RK66C","client_version":""}}"}
```

含义：**字段名、类型、层级全部正确**，10104 只是「token 校验不过」。
也就说：只要拿到合法 token，这条链路立刻通。

微信侧同理：

```
{"errMsg":"type:business, code:40029, msg:MlolLoginByWechat fail ret=40029","result":1025}
```

40029 是微信的标准错误码「invalid code」。**注意它证明了一件事：AppSecret 在掌瓦服务端**，
服务端替我们做 code→openid 交换 —— 所以我们不需要 AppSecret，但也意味着 code 必须由
**掌瓦自己的 appid** 签发（微信按 appid 隔离 code），自建网站应用扫出来的 code 一定 40029。

### 5.3 致命的那一跳：DNS 黑洞

```
$ dig +short @223.5.5.5 ptlogin4.openmobile.qq.com   → 0.0.0.1
$ dig +short @119.29.29.29 ptlogin4.graph.qq.com     → 0.0.0.1
$ dig +short @223.5.5.5  ptlogin4.web.qq.com         → 0.0.0.1
```

对照还活着的主机：

```
ptlogin4.qq.com       → ins-n4bmeqrn.ias.tencent-cloud.net（403 = 活着）
ptlogin2.qq.com       → 活着
ssl.ptlogin2.qq.com   → 活着
xui.ptlogin2.qq.com   → 活着（出码/轮询就是用它）
```

`ptlogin4.openmobile.qq.com` 正是 `check_sig` 完成后 302 到 `auth://tauth.qq.com/#access_token=…`
的那台机器。它被指到 `0.0.0.1` 之后：

- 扫码 → 手机确认 → `ptqrlogin` 返回 `code=0`（全对）
- 跟 302 去换 token → 连不上 → 拿不到 `access_token`
- 换主机名？`ptlogin4.qq.com` 认路径但认不出这套 `sigx`，302 回 `s_url` 且不带 token

这不是网络问题（三个公共 DNS 一致），也不是参数问题（同参数能出码、能确认）。

## 六、那还有哪些真的能走通

### A. 手动喂 token（本次新增，最实用）

```bash
node tools/mval-login.mjs qq --openid=<openid> --token=<access_token> --user=<QQ号> --write
node tools/mval-login.mjs wx --code=<掌瓦appid签发的code> --user=<QQ号> --write
```

换票 → 认角色 → 取 scene → 直接写 `bridge/accounts/<QQ号>.json`（跟 `#瓦导入` 同一套格式）。
只要你能从任何渠道拿一份合法 token，这一步就不需要抓两次包。

### B. 抓包导入（现有）

`#瓦导入 <cURL>` 仍然是最稳的。票据硬 3 天，到期重抓。

### C. 设备侧提取（需要 root，未实现）

掌瓦把登录态存在 MMKV：`/data/data/com.tencent.apps.valorant/files/mmkv/wg_license_cache`，
字段 `userId / openId / token / webToken / ssoOpenId / ssoUin / authType`。
有 root 的机器上 `adb shell su -c "cat …"` 就能拿到，再解析 MMKV 格式即可。
这条路能完全免抓包，但依赖 root，本次没做。

### D. 不要做的

- 拿自建微信网站应用的 code 去换掌瓦凭证（必然 40029）
- 用旧 `jsver` 轮询（会被判非本客户端，返回空 body）
- 期待「换个 QQ appid 的 token」能过（10104）

## 八、第二轮：两条扫码链路是怎么打通的

### 8.1 微信 —— 扫码 SDK（`sdk/qrconnect`）

#### 发现过程

在 DEX 字符串池里搜 `qrconnect`，一次捞到三条：

```
/go/auth/get_sdk_ticket
https://open.weixin.qq.com/connect/sdk/qrconnect?appid=%s&noncestr=%s&timestamp=%s&scope=%s&signature=%s
https://long.open.weixin.qq.com/connect/l/qrconnect?f=json&uuid=%s
```

然后 `dexxref2.py` 定位到引用它们的类：`com.tencent.wglogin.authsuite.c$1`。

#### 关键代码（`wglogin/authsuite/c.java`）

```java
public static void a(Activity activity, final a aVar) {   // loginWXByQRCode
    new GetWXServerTicketProtocol().post(activity, … {
        public void onSuccess(GetWXServerTicketResult r, boolean z) {
            String appid = com.tencent.wglogin.authsuite.util.a.b;   // 运行时注入
            String noncestr = e.a(6);
            String ts = (System.currentTimeMillis() / 1000) + "";
            String origin = "appid=" + appid + "&noncestr=" + noncestr
                          + "&sdk_ticket=" + r.ticket + "&timestamp=" + ts;
            String sign = f.a(origin);            // sha1
            DiffDevOAuthFactory.getDiffDevOAuth()
                .auth(appid, "snsapi_userinfo", noncestr, ts, sign, listener);
        }
    });
}
```

`DiffDevOAuthFactory` 就是微信官方的 `libammsdk` 里的 `DiffDevOAuth`，
它内部做的事正好对应上面那两条 URL：出码 + 长轮询。

#### 三个必须对齐的参数

| 参数 | 值 | 来源 |
|---|---|---|
| `appid` | `wxcbb49f1f39656c2a` | `com.tencent.mlol.startup.afterlaunch.h` 的掌瓦分支（`c.g()`） |
| `scope` | `snsapi_userinfo` | 上面那行 `auth(...)` 里写死 |
| `ticket` | POST `/go/auth/get_sdk_ticket` 返回 | 免鉴权，body 传 `{clienttype:9, config_params:{...}}` |

> ⚠️ 同一个 dex 里还有 `wx5a4a8ac0fd48303a`，那是**掌上英雄联盟**的（`c.f()` 分支）。
> Gson/常量都在同一个文件里，很容易抓错。

#### 实测证据

```
[1] ticket: {"data":{"ticket":"qeuRRdzufZaOpdhfU2Q4gGbgoxq-…"},"result":0}
[2] raw:    appid=wxcbb49f1f39656c2a&noncestr=11ce2b4a6121d8da&sdk_ticket=…&timestamp=…
[3] HTTP 200 len 68700
    errcode=0, uuid=061lJR7z2qTgnl2d, appname=掌上无畏契约
[4] poll → {"wx_errcode":408, "wx_code":""}
```

`appname` 回显「掌上无畏契约」是最有力的确认：服务端认这个 appid 属于掌瓦。

#### 换票字段（`LoginByWXProtocol`）

```java
@Protocol(path = "/go/auth/login_by_wechat")
class Params {
    ConfigParams config_params;   // { client_dev_name, lang_type=0 }
    LoginInfo    login_info;      // { appid, code, wx_info_type=1, check_third_type }
    String       mcode;
    int          clienttype = AppContext.h();     // 9
    int          mappid     = util.a.c;           // login_mappid
}
```

`check_third_type` 在 `wglogin.d#a(SsoLicense, f)` 里写死为 **1**（早期实现里我写了 0，
实测 0/1 都能过参数校验、都回 40029，但按 APK 应该用 1）。

### 8.2 QQ —— 页面式授权（绕开 `check_sig`）

#### 死在哪，以及为什么那不是唯一的路

纯 HTTP 追 `ptqrlogin` 的返回值时，`code=0` 给的 redirect 指向
`ptlogin4.openmobile.qq.com/check_sig?...`，而这台机器的 DNS 被指到 `0.0.0.1`：

```
$ dig +short ptlogin4.openmobile.qq.com @223.5.5.5   → 0.0.0.1
$ dig +short ptlogin4.graph.qq.com      @119.29.29.29 → 0.0.0.1
$ curl https://ptlogin4.openmobile.qq.com/           → 000（连不上）
```

但**新流程不用它**。看 `m_authorize` 返回的跳转页：

```js
var src = "https://xui.ptlogin2.qq.com/cgi-bin/xlogin?appid=716027609
          &pt_3rd_aid=102061775&daid=381&…&h5sig=MfBler9YgYCaIkB91wdEHEiRvJzgTqz6JTw7_14YvYM&loginty=7";
location.replace(src);
```

`loginty=7` + 服务端下发的 `h5sig` 走的是 openapi 版授权，
二维码确认后页面去 `openmobile.qq.com/oauth2.0/m_authlist`：

```
$ curl "…/m_authlist?appid=716027609&pt_3rd_aid=102061775&…&loginty=7"
HTTP 200 size=4246
<title>QQ登录</title>
<p id="auth_tips">掌上无畏契约将获得以下权限:</p>
```

—— 也就是说，**授权这一步发生在 `openmobile.qq.com` 上，那台是活的**。
`check_sig` 是给旧版（`loginty=6`）用的落点，走错了分支。

#### 所以改成让浏览器跑

浏览器负责跑完页面 JS，我们只听三个信号（哪个先响算哪个）：

| 信号 | 命中场景 |
|---|---|
| `page.on('request')` | `auth://tauth.qq.com/#access_token=…` |
| `page.on('framenavigated')` | 同上，导航不一定产生 request |
| 轮询 `location.href` | 兜底 |

回调里**没有 openid**（`response_type=token` 只给 `access_token` / `pay_token`），
要另外用 `graph.qq.com/oauth2.0/me?fmt=json` 换。

#### 出码实测

```
[qq-page] 打开授权页：…/m_authorize?client_id=***&…&style=qr
✅ qq 出码成功（8898ms）  二维码 264×264 PNG
   poll#1: status=waiting msg=等待扫码
```

页面里的真码是 `<img id="qrimg" src="https://xui.ptlogin2.qq.com/ssl/ptqrshow?s=8&…">`。
`#qrimg` 这个 id 是最早漏掉的选择器 —— 页面上还有个空的 `#imgVerify`，
只看 `img` 标签会抓错。取图方式改为「拿页面 cookie 回源拉 `ptqrshow`」，
得到的是原始 264×264，比截屏清晰。

#### 保险丝

万一流程真走到黑洞主机，`qqpage.js` 会在 `page.on('request')` 里 `abort` 掉，
把同一条 `check_sig` 的 path/query 改投到还活着的 `ptlogin4.qq.com`
（实测：无效 sigx 会 302 到 www.qq.com，说明它认这套参数）。

### 8.3 两条链路的最终形状

| | QQ | 微信 |
|---|---|---|
| 出码 | 浏览器打开 `m_authorize` | 纯 HTTP `sdk/qrconnect` |
| 二维码 | `<img id="qrimg">` 回源 264×264 | `qrcodebase64`（JPEG 62KB） |
| 拿凭证 | `auth://` fragment 的 `access_token` | 轮询 `wx_errcode=405` 的 `wx_code` |
| 补全 | `graph/me` → `openid` | 无（code 直接给掌瓦） |
| 换掌瓦凭证 | `login_by_qq` | `login_by_wechat` |
| 依赖 | 一个 Chrome/Chromium | 无 |
